# Lock outdated pitfall — full transcript & reproduction

## Session context
- **Date:** 2026-06-21
- **Project:** `<app>` — Phoenix 1.8 + Ecto + LiveView app
- **Stack:** Elixir 1.20.1 / OTP 29, mise-managed
- **Deploy target:** Coolify via Nixpacks (autogenerated Dockerfile)
- **Triggering dep:** `:heroicons` (git-based, `tailwindlabs/heroicons`, sparse `optimized`)

Also present in the same log (separate concern, not blocking the build):

  (ENV "APP_PASSWORD" / ENV "SECRET_KEY_BASE" / ARG "APP_API_TOKEN" / ARG "APP_PASSWORD" / ARG "SECRET_KEY_BASE" / ENV "APP_API_TOKEN")

## State before the fix

`mix.exs`:
```elixir
{:heroicons,
 github: "tailwindlabs/heroicons",
 tag: "v2.2.0",
 sparse: "optimized",
 app: false,
 compile: false,
 depth: 1},
```

`mix.lock`:
```
"heroicons": {:git, "https://github.com/tailwindlabs/heroicons.git", "0435d4ca364a608cc75e2f8683d374e55abbae26", [tag: "v2.2.0", sparse: "optimized", depth: 1]},
```

Lock and `mix.exs` both reference `v2.2.0`, but the lock has the commit SHA baked in from a previous `mix deps.get`. Mix in `:prod` compares SHAs, sees a mismatch in how the entry is described, and aborts.

## Reproduction (local)

1. Have a project with a git-based dep pinned by `tag:` in `mix.exs` but with a commit SHA in `mix.lock`.
2. Run `MIX_ENV=prod mix compile` locally.
3. Observe: same `lock outdated` error as the deploy log.

Local `:dev` build (`mix compile` without `MIX_ENV=prod`) does **not** reproduce the failure — Mix is permissive in dev. This is why dev passes but deploy fails.

## Resolution steps that worked

1. Read `mix.lock` to extract the exact commit SHA the lock has.
2. Update `mix.exs` to pin by `:ref` with that SHA:
   ```elixir
   {:heroicons,
    github: "tailwindlabs/heroicons",
    ref: "0435d4ca364a608cc75e2f8683d374e55abbae26",
    sparse: "optimized",
    app: false,
    compile: false,
    depth: 1},
   ```
3. Run `MIX_ENV=prod mix deps.get` to align the lock entry style.
4. Verify: `MIX_ENV=prod mix compile` → compiles clean, `Generated <app> app`.
5. Run the project `precommit` alias (`mix precommit` in this repo = compile + format + test) to confirm nothing else broke.
6. Commit `mix.exs` and `mix.lock` together; push.

## Verification commands used

```bash
# Local prod build (the actual fix verification)
MIX_ENV=prod mix deps.get
MIX_ENV=prod mix compile

# Full precommit (catches the rest of the AGENTS.md guidelines)
mix precommit
```

Expected outputs: `Generated <app> app` for the compile step, and `5 passed` (or similar) for the test step. The Phoenix project's `AGENTS.md` mandates running `mix precommit` before declaring work done.

## Lock diff after the fix (informational)

The `mix.lock` entry style updates from `[tag: "v2.2.0", sparse: "optimized", depth: 1]` to `[ref: "0435d4ca36...", sparse: "optimized", depth: 1]`. The actual commit SHA is unchanged — only how it's described. This is why both `mix.exs` and `mix.lock` should be committed in the same change.

## What this does NOT fix

The `SecretsUsedInArgOrEnv` warnings from the same Coolify log come from a Dockerfile (custom or Nixpacks-generated) that uses `ARG` or `ENV` for `APP_PASSWORD`, `SECRET_KEY_BASE`, `APP_API_TOKEN`. That's a separate, broader concern about how secrets are injected at build vs runtime. Locking deps correctly does not silence those — fixing them requires moving the secrets to runtime-only env injection (e.g., Coolify env vars, BWS, Docker secrets, multi-stage builds with `ARG` only used as a token to fetch a real secret, not as the secret itself).

## Other notes from the same session

- Mix was invoked through `mise exec -- mix ...` because `mix` is not on `$PATH` directly. The mise-managed Elixir 1.20.1 / OTP 29 stack is what the project uses.
- `nixpacks.toml` / `Dockerfile` / `coolify.yaml` were not present in the repo — Nixpacks generated the Dockerfile from its Elixir detector. If you need to control the build (e.g., to silence the secrets warnings), author a `Dockerfile` and tell Coolify to use it instead of Nixpacks.
