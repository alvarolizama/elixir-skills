# Phoenix Feature Removal

Borrar un feature ENTERO de una app Phoenix sin dejar referencias huérfanas ni romper la suite. Distinto de revertir un commit: a veces el feature abarca varios commits + archivos nuevos + migraciones + docs.

## When to Use

- Álvaro dice "borra X", "quita el chat", "elimina el feature Y" en un repo Phoenix.
- Revertir un feature multi-commit a estado previo (`git show <sha>:<file>`).
- **Removing a single dependency** (`{:dep, "~> x.y"}` from `mix.exs`) — lighter than a full feature removal but the same verification applies: grep for references, remove them, unlock, compile. See the "Dependency removal" pitfall below.

## Map of Blast Radius (checklist antes de borrar)

Buscar TODAS las piezas del feature con `search_files` + grep del nombre y aliases:

| Capa | Qué buscar |
|------|-----------|
| **Módulos backend** | `lib/<app>/<feature>/*.ex` — servicios, GenServers, schemas |
| **Supervisión OTP** | `application.ex`: children del feature (Supervisor, Registry) |
| **Web** | Componentes LiveView (`lib/<app>_web/components/`), mounts en `layouts.ex`, attrs exclusivos del layout, rutas en `router.ex` (live + scope API) |
| **Tests** | `test/` espejo de cada módulo borrado |
| **DB** | Tablas del feature → nueva migración `drop_if_exists table(...)` vía `mix ecto.gen.migration drop_<table>` |
| **Docs** | README (features, screenshots, tablas), SKILL.md, docs Live (`docs_live.ex` — guías Y endpoints muertos del API reference), `references/*.md` |
| **Assets** | Screenshots huérfanos en `docs/screenshots/`, imports en `app.js`/`app.css` |
| **Gettext** | `mix gettext.extract && mix gettext.merge priv/gettext` DESPUÉS de borrar el código — limpia msgids automáticamente |
| **Env vars / config** | Vars exclusivas del feature en `.env` / `config/*.exs` |

**Regla:** antes de borrar attrs del layout, grepear que NADIE más los pase: `grep -rn "page_slug=\|view_type=" lib/<app>_web/ | grep -v <feature>`. Attrs con el mismo nombre usados por componentes locales NO cuentan (verificar el contexto).

## Revert vs Delete

- **Revert a commit previo** (el feature fue reciente y lineal): `git show <sha_previo>:<path> > <path>` por archivo tocado + `git rm` de archivos nuevos. Verificar después con `git show <sha>:<path> | diff -q - <path>` por archivo.
- **Delete forever** (el feature se queda en historia pero no en main): `git rm` + edits manuales + migración de drop.

## Subagent Wave Split (si Álvaro pide subagentes)

Scopes DISJUNTOS por capa, nunca dos agentes en el mismo archivo:

1. **Backend**: módulos + supervision + tests backend.
2. **Frontend**: componentes + layout attrs + tests web.
3. **Docs/DB/i18n**: README, gettext, migración, screenshots.

Cada prompt debe listar archivos exactos y prohibir tocar los de otros agentes. Verificar yo mismo (parent) con grep + compile + suite antes de commitear — NUNCA confiar solo en el self-report del subagente.

## Verification (obligatoria, en orden)

1. `grep -rn "<FeatureName>\|<feature_name>" lib/ test/` → CERO referencias.
   Scope the grep to **feature-specific identifiers** (`daily_note|ensure_daily_note|daily-note`), NOT generic single words — bare `Daily` also matches unrelated strings like agent schedules (`"Daily 06:00"` in docs_live). `search_files` with count-mode + a scoped pattern is the fastest sweep; leftover matches in `_build/`/`deps/`/`.git/` are cache/history and don't count.
2. `mix compile --warnings-as-errors` limpio.
3. `mix test` — comparar fallos contra pre-existentes (confirmar con `git stash` si dudo).
4. Migración: `mix ecto.migrate` en dev Y test; verificar `\dt <table>` ausente en psql.
5. Server smoke: levantar `mix phx.server`, login + curl 200 en páginas principales + MCP/REST clave del app.
6. `mix precommit`.

## Partial Feature Relocation (distinct from full deletion)

> For the mechanical tab/feature removal within LiveViews — shared-assign
> handling, orphaned-helper sweep under `--warnings-as-errors`, cross-file
> component renames breaking reverts, and sibling-subagent reverting files
> mid-task — see `references/liveview-tab-feature-removal.md`.
>
> For **merging a whole feature page into an existing LiveView** (e.g.
> alerts → logs as sections, with KPI cards, tables, filters, CSV export,
> PubSub toasts, and sidebar badge) — see
> `references/feature-merge-into-liveview.md`. Also covers grouped
> pagination ("ver más" per group) and layout fixes after element removal.

A "removal" task is sometimes a **relocation**: the feature's UI moves to a
dedicated LiveView (or is replaced by a link out to a new page), but the
backend modules, DB schema, and routes stay. The old per-page UI (kanban
board inside GoalLive, drag-and-drop columns, JS hooks, status helpers) is
deleted; a *link* to the new home replaces it.

Example pattern (MyApp kanban relocation, Phase 3):
- Old: `GoalLive` had `@kanban_columns`, a `GoalKanban` JS hook + `<script>`
  block, `handle_event("move_todo")`, and `goal_kanban_status/1` /
  `goal_column_items/2` / `goal_column_count/2` helpers, plus a full kanban
  HEEx board in the "todos" tab.
- New: the "todos" tab renders a **simple list** of todos + a single
  `<.link navigate={~p"/kanban?goal=#{@page.slug}"}>Open in Kanban</.link>`.
  A dedicated `KanbanLive` owns the board UI.

### What to delete vs keep

| Delete | Keep |
|--------|------|
| `@kanban_columns` assign | `@goal_todos` / `@plan_todos` list loading |
| JS hook (`<script :type={...ColocatedHook} name=".GoalKanban">`) | The simple list HEEx |
| `handle_event("move_todo", ...)` | Other `handle_event` clauses |
| `goal_kanban_status/1`, `goal_column_items/2`, `goal_column_count/2` | A new `kanban_status/1` + `kanban_status_class/1` (simple badge helpers for the list) |
| Full kanban board HEEx block | Status/meta helpers used elsewhere |

### Blast-radius check (additions to the standard map)

- `~p"/kanban?goal=#{slug}"` and `~p"/kanban?plan=#{slug}"` links: greppable
  via `~p"/kanban\?`.
- The **new** dedicated LiveView (`KanbanLive`) and its route must already
  exist (or be added in a parallel task) — otherwise the `~p` links fail
  compile. See `phoenix-liveview-debugging` → "`~p` Route Sigil
  Compile-Time Verification".
- Sidebar/dashboard/command-palette entries pointing at the new home
  (`/kanban`, `/projects/new`) may reference routes that don't exist yet in a
  phased refactor — use string literals, not `~p`, until the routes land.
- Gettext: any **new** strings added to the replacement UI (e.g.
  `gettext("Open in Kanban")`, `gettext("todos linked")`) need
  `mix gettext.extract --merge` after the code lands. Watch for **fuzzy**
  matches (gettext reuses a nearby old msgid's translation — e.g. "Create
  Project" inherits "Crear nota" from the deleted "Create Note" entry).

### Sidebar / nav rewrites

When the relocation comes with a sidebar reorg (new groups, new order, dropped
entries), update `compute_counts/1` to add the count key for the new page
type (`projects: by_type["project"]`) — a missing count key renders `nil` in
the badge, not `0`, which surfaces as a blank badge instead of "0".

### Verification sequence (same as full deletion, plus)

1. `grep -rn "GoalKanban\|move_todo\|goal_kanban_status\|@kanban_columns"` → 0
   in the file you refactored (the dedicated LiveView may still define its own
   kanban helpers — that's fine, scope the grep to the file you touched).
2. `mix compile --warnings-as-errors` clean.
3. `mix test` — if tests referenced the deleted helpers/events, update them by
   swapping kanban assertions for list assertions (e.g.
   `assert has_element?(view, "[data-test=todo-row]")` instead of
   `assert has_element?(view, "[data-kanban-status]")`). If no tests
   referenced the deleted UI, the suite passes unchanged.
4. `mix gettext.extract --merge` and review fuzzy entries.

## Common Pitfalls

- **Attr de layout compartido:** un attr con nombre genérico (`page_type`) puede existir en el layout Y en componentes locales — borrar solo si el layout es el único consumidor.
- **Endpoints documentados pero muertos:** el API reference en `docs_live.ex` puede listar rutas que ya no existen en el router — borrar la entrada del TOC y de la tabla de endpoints.
- **Migración "already up" pero tabla viva en test:** si `schema_migrations` registra la versión pero la tabla sigue (p.ej. gen.migration corrió algo raro), hacer `DROP TABLE IF EXISTS` manual en la DB de test y seguir — la suite no recrea tablas.
- **Gettext fuzzy:** tras extract/merge, revisar msgids nuevos marcados `fuzzy` — gettext adivina traducciones viejas que no aplican (p.ej. "Max pages" → "Pasos máximos"); corregir el msgstr y quitar el flag.
- **Tests flaky pre-existentes:** no atribuirlos al borrado — confirmar con stash ANTES de commitear que fallaban igual sin los cambios.
- **Env vars en .env ignoradas por .gitignore:** `git add .env` falla silenciosamente — editar con `sed -i ''` y verificar con grep.
- **Handlers huérfanos al borrar tabs/paneles:** cuando quitas un tab o panel del UI, los `handle_event("event_name", ...)` que sus botones disparaban se quedan como código muerto en cada LiveView. No rompen compilación ni tests, pero son basura. Después de borrar el panel, grepear `phx-click="event_name"` → si 0 hits en templates, los handlers en los LiveViews ya no tienen quien los dispare. Caso MyApp: al quitar los tabs de "Relations" y "Versions" de `page_components.ex`, los handlers `compare_version`/`clear_compare` quedaron huérfanos en 8+ LiveViews (note_live, todo_live, goal_live, etc.) delegando a `DranWeb.VersionCompare`. Limpiar: borrar los `handle_event` + el assign `compare_version` + el module `VersionCompare` si ya nadie lo usa. Verificación: `grep -rn "compare_version\|clear_compare" lib/` → si solo aparecen en el module `VersionCompare` y su test, todo lo demás se puede borrar.
- **Sidebar collapsibles al borrar tabs:** si los tabs que quitaste (Relations, Versions) tenían paneles en el sidebar o en el main column, convierte los que se quedan (Metadata, Links/Backlinks, Changelog, Activity) en `<details>` colapsables para que el sidebar no se vea vacío con contenedores `surface-2` planos. Receta: envolver cada `<div class="surface-2 rounded-lg p-4">` en `<details class="group surface-2 rounded-lg p-4">` con `<summary>` + chevron icon. Si el componente interno ya tiene `<details>` anidados (ej: `backlinks_section`), aplanarlo a divs+headers para evitar details anidados.
- **Unificación de tabs al borrar:** al quitar tabs duplicados (ej: `tabs_bar` dentro de `<:tabs>` cuando `page_detail` ya tiene su propia barra), usar `execute_code` con regex para limpiar mecánicamente 8-9 LiveViews a la vez: borrar `<.tabs_bar>`, `@tabs`, `tabs: @tabs`, y el wrapper `<div :if={@active_tab == "content"}>`. Cuidado con el `</div>` huérfano que deja el wrapper removido — fix regex: `re.sub(r'(<% end %>)\\s*</div>\\s*(</:tabs>)', r'\\1\\n          \\2', content)`. Para LiveViews con múltiples tabs (Plan con "content"+"todos"), manejar manualmente — el tab extra se convierte en `:extra_tabs` y su contenido va a `:extra_content`. Ver `phoenix-heex-design-system` → `references/unified-tab-bar-architecture.md`.
- **Regex en mcp.ex para borrar tools/prompts:** cuando borres tools MCP del `@tools` o prompts del `@prompts` en `mcp.ex`, los regex multilinea con `re.DOTALL` pueden dejar fragmentos huérfanos (el `%{ "name" => "dran_X" }` se borra pero el `inputSchema` con propiedades queda flotando, o viceversa). Síntoma: `SyntaxError: unexpected token: }` o `unclosed delimiter`. Fix: después del regex, leer las líneas alrededor del error con `read_file`, identificar el bloque roto (props huérfanas sin `%{` padre, o `},` sin apertura), y borrar manualmente con `patch` el rango exacto. También cuidar los `defp start_agent_by_type("X"...)` y `defp execute_tool("X"...)` que son funciones separadas del bloque `@tools`.
- **Subagent timeout con trabajo parcial:** cuando un subagent hace timeout (600s) pero ya hizo cambios parciales, verificar con `git diff --stat HEAD` qué archivos tocó. Si la mayoría de los cambios están hechos (ej: 20 archivos modificados, archivos borrados), conviene terminar el trabajo a mano en vez de re-dispatchar. Pasos: (1) `mix compile --warnings-as-errors` para ver si compila, (2) `grep -ri "<term>" lib/ test/ priv/` para ver qué referencias quedan, (3) limpiar archivo por archivo con `execute_code` o `patch`. Patrones típicos del subagent timeout: borró archivos pero no limpió referencias en mcp.ex, docs_live.ex, settings_live.ex, gettext files.
- **UI Control Removal (lightweight, not full feature):** when the user says "quita esto/estos" or "quit esto" while pointing at a UI element via the Hermes element picker, the task is removing individual controls (selects, badges, indicators, buttons) — NOT entire features. Lighter than full feature removal but same discipline. Blast-radius checklist for a single control:
  1. **Template**: remove the element (form, select, badge, div) from the `.html.heex`
  2. **handle_events**: if the control fired events (`phx-change`, `phx-click`), remove the `handle_event` clauses — they become unreachable code
  3. **Assigns**: check each assign the removed template used (`@model_filter`, `@models`, etc.) — remove from `mount` / `handle_params` if NO OTHER template references them
  4. **Private helpers**: functions that ONLY fed the removed assigns (e.g. `scoped_teams/1`, `build_path/2`, `maybe_put/3`) become dead code — delete them
  5. **Aliases**: remove unused `alias` lines that no remaining code references
  6. **Tests**: remove or update tests that assert on the removed elements (`#topbar-my-budget`, `#model-filter-form`, etc.)
  7. **Verify**: `mix compile --warnings-as-errors` → `mix test` affected file → `mix test` full suite
  **Key pitfall**: don't just remove the template — the backend code (events, assigns, helpers) silently becomes dead code that may not warn but wastes queries / pollutes assigns. Always sweep the full chain. This session (2026-08-03) removed the topbar indicators (budget chip + admin badges + online/inflight) and stats filter selects (models/teams/services) from MyApp using this exact sequence — 215 tests passed post-cleanup.
  **Layout fix**: after removing an element from a flex container with `justify-between`, the remaining element(s) hug the left edge. Change to `justify-end` to keep them right-aligned (common for CSV export buttons that used to sit next to a select). See `references/feature-merge-into-liveview.md` → "Layout Fix After Element Removal".
  **Grid fix**: after removing a card from a responsive grid (`grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-5 gap-4`), adjust the column count (`lg:grid-cols-4`) in the SAME edit — otherwise the row renders 4 cards + an empty slot. MyApp 2026-08-07: removed the "Actividad" KPI card (live-indicators) from `/dashboard/logs`, grid went 5→4 columns.
  **Assign-consumer check before deleting the chain**: an assign may feed OTHER live UI beyond the removed card. In the same MyApp edit, `api_inflight` also drove the "pending in-flight" rows in the logs table (via `Inflight.list()` + `stream_insert`), so the handler chain (`:refresh_inflight`, `:inflight_started`, `:inflight_done`) had to STAY — only the display counter went. Before deleting a handler/subscription/PubSub topic, grep each assign it updates: if another template section reads it, keep the flow and remove only the display. Example: `online_users` fed ONLY the card → also removed the `Presence.topic()` subscription + `presence_diff` handler; `api_inflight` fed the card AND the pending flow → kept the flow, dropped the counter. Verify with `grep -n "assign_name" file.ex` — template hits are the consumers that matter.

- **Bulk test cleanup con execute_code + regex:** cuando un subagent timeout deja 10+ archivos de test con referencias huérfanas a una variable eliminada (ej: `org`), usar `execute_code` con Python regex para limpiar mecánicamente todos a la vez. Patrones regex efectivos: (1) borrar lineas que crean la variable `org`: `re.sub(r'\{\:ok,\s*org\}\s*=\s*Accounts\.create_organization\(%\{[^}]+\}\)\s*\n', '', content)`, (2) borrar `organization_id: org.id,` de maps: `re.sub(r'\s*organization_id:\s*org\.id,?\n', '\n', content)`, (3) borrar la variable de pattern matches: `re.sub(r'org:\s*org,?\s*', '', content)`, (4) renombrar funciones: `content.replace("list_enabled_rules_for_org(", "list_enabled_rules(")`. Despues del regex masivo, quedan refs que la regex no capturo (variables `org` en strings, params de funciones, struct literals con `organization_id:`) — compilar para encontrar los errores y arreglar manualmente con `patch` archivo por archivo. Si aun quedan muchos, despachar un segundo subagente especifico para limpiar los refs restantes. Usar `search_files` con `output_mode=count` para ver que archivos aun tienen refs.
- **Mover paneles al área de contenido:** cuando el `detail-panel-graph` o `detail-panel-related` quedaban fuera del two-column layout (después del sidebar), moverlos dentro de la columna principal (`<div class="flex-1 min-w-0 space-y-6">`) junto con `extra_content`. Si no, el graph se renderiza abajo del sidebar en vez de al lado.
- **Borrar un page type entero (ej: `comparison` en MyApp):** es más que borrar un módulo — el tipo vive en la validación del schema, la lista de cast del meta, y la DB tiene páginas existentes. Checklist: (1) `page.ex`: quitar del `@page_types` list + moduledoc; (2) `page_meta.ex`: quitar los `field` del embedded schema **Y** de la lista `all_fields()` del `cast` **en el mismo paso** — si solo quitas los fields, el cast truena con `ArgumentError: unknown field :entities given to cast` en TODOS los tests que crean páginas (8+ tests fallan a la vez); (3) `page_types.ex`: entry del map (path/label/icon/plural) + los `gettext("X")` msgids del bloque i18n; (4) LiveView + rutas del router; (5) sidebar `layouts.ex`: nav item, entry del `@nav_key_page_types` map, count en `compute_counts`; (6) dashboard: nav group entero si queda vacío + `type_order` en `sort_by_type`; (7) `search_live.ex`: `type_chip_bg`/`type_icon_color`/`type_badge` clauses; (8) `page_new_live.ex`: `type_to_page` clause + listas de labels (ojo con la lista `feminine` gender-aware para español); (9) `page_list_components.ex`: empty-state clause; (10) `journey.ex` + `graph_helpers.ex`: color hex del type — el test `type_colors` falla con `map_size(colors) == N` off-by-one; (11) mcp.ex: enums `"type"`, descripciones, doc de meta fields; (12) **migración de datos** — las páginas existentes con ese tipo rompen la validación al boot: `execute("UPDATE pages SET page_type = 'note', meta = meta || '{\"kind\": \"thought\"}'::jsonb WHERE page_type = '<type>'")`; (13) `mix gettext.extract && mix gettext.merge priv/gettext` DESPUÉS de borrar el código (limpia 80+ msgids obsoletos de una); (14) tests que usan el tipo como ejemplo (brain_test con disabled_page_types, page_meta_test) — cambiar a otro tipo. **Orden crítico:** fields + cast list juntos ANTES de correr tests.
- **Quitar un page type toca el SKILL.md de punta a punta:** el tipo aparece en: frontmatter description, tabla de page types, decision tree de creación, recipes (puede haber receta completa del tipo), y common mistakes. Si el SKILL.md ya está desactualizado en otros frentes (agentes quitados, features nuevas sin documentar), un **rewrite completo** enfocado puede ser mejor que 10 patches parciales — ocurrió al quitar `comparison`: el SKILL.md aún mencionaba el agente ask y weekly reviews, así que se reescribió entero (612→280 líneas) resolviendo todo de un jalón.
- **Borrar agentes del codebase:** además del módulo del agente (`lib/MyApp/agent/X.ex`), limpiar: (1) `agent_type` en el enum de mcp.ex, (2) descripción del tool `dran_start_agent` en mcp.ex, (3) UI del agente en docs_live.ex (`agents_data()` function), (4) sidebar nav en layouts.ex, (5) settings_live.ex (referencias como `research_lang`), (6) tests que usen `agent_type: "X"`, (7) `behaviour.ex` que documenta el agent_type string, (8) `scripts/mcp_smoke.sh` (el `want` set del enum de agent_types), (9) secciones de docs_content.ex que documentan el agente (renumerar las secciones subsecuentes), (10) **crons en config/config.exs** (Quantum jobs del agente — `weekly_review` tenía `schedule: "0 8 * * 0"`). **Funciones huérfanas de Brain:** al borrar un agente, buscar funciones de `brain.ex` que SOLO ese agente llamaba (ej: `expand_neighbors/2` era exclusiva del agente QA — GraphRAG) — borrar la función + sus tests, o queda dead code con suite verde. Verificar con `grep -rn "Brain.func_name" lib/ test/`: si solo aparece en brain.ex y su propio test, es huérfana. Tests que usan `agent_type: "ask"` como STRING de ejemplo (session_test, brain_test insertando Sessions históricas) NO necesitan cambio — el campo es free-form.
- **Borrar funciones grandes con sed line-deletion (backup + verify obligatorios):** cuando una función a borrar en un archivo grande (>100 líneas incluyendo heredoc `@doc`) hace frágil el `patch` (old_string muy largo o con triple-quotes), usar sed con rango de líneas: (1) `cp file.ex /tmp/backup.ex`, (2) localizar límites con `grep -n "def func_name"` y `sed -n 'X,Yp'` para confirmar la línea exacta del `end` de cierre (ojo: el bloque incluye comentario de sección `# ───` + `@doc` + función), (3) `sed -i '' 'START,ENDd' file.ex`, (4) INMEDIATAMENTE `sed -n` alrededor del corte para verificar que no quedó `end` duplicado ni función partida a la mitad, (5) `mix format` + `mix compile --warnings-as-errors`. El error típico es cortar 1 línea de más o de menos — la verificación visual post-sed es obligatoria. Después, helpers del test file asociado quedan sin uso (ej: `find_by_slug`) y `mix compile` NO los reporta en archivos de test — grepearlos y borrarlos manualmente.
- **Tool count en tests:** después de borrar un MCP tool, el test `tools/list returns exactly N tools` falla con un off-by-one. Buscar `assert length(tools) == N` en `mcp_full_test.exs` y ajustar el número.
- **Cast helpers huérfanas al quitar settings:** al borrar un setting (ej: `daily_note_enabled`), la función cast de ese tipo (ej: `cast_bool/1`) queda sin uso y `mix compile --warnings-as-errors` truena con `warning: function cast_bool/1 is unused`. El warning aparece típicamente DESPUÉS del `gettext.extract`/`merge` (que quita la UI pero deja el handler), así que la secuencia correcta es: borrar código + UI → gettext extract/merge → compile con warnings-as-errors → borrar el helper huérfano + su comentario → re-compile.
- **Secciones de seeds/scripts:** al quitar una sección numerada de `seeds.exs` (o similar), el contenido actual puede haber cambiado (ej: un merge previo insertó un `...`). SIEMPRE re-leer el bloque exacto con `read_file` antes del patch; un old_string aproximado puede duplicar contenido en vez de borrarlo. Después del borrado, re-leer alrededor del corte pa' confirmar que no quedó basura ni `end` duplicado.
- **Dead code audit (post-removal sweep):** después de borrar features, hacer un audit de código muerto con `execute_code` + Python: (1) listar todos los `def` públicos de `lib/` con regex `^\s*def\s+(\w+)`, (2) para cada uno, grep en todos los `.ex`/`.exs` buscando `Module.func` o `ShortMod.func`, (3) reportar los que tienen 0 callers externos. Falsos positivos comunes: controllers (llamados por router), plugs (pipeline), components (llamados desde HEEx), OTP callbacks (`start_link`, `init`, `handle_*`). También buscar módulos completos sin referencias: `grep -rl "ModuleName" lib/ test/` — si solo aparece en su propio archivo, es candidato. Verificar con `git blame` antes de borrar — algunos son deliberate boundaries (release tasks, compat shims). Receta MyApp: tras borrar artifacts+research+ingest, el audit encontró `Brain.list_versions`, `Brain.resolve_links`, `CoreComponents.translate_errors`, `TodoHelpers.priority_class`, `LocaleController`, `PageHTML` como código muerto real, y `MyApp.Release` como falso positivo (usado por scripts de release en `rel/overlays/bin/`).
- **Borrar inference modules sin consumers:** patrón específico: módulos de inferencia (ASR, Vision, Markitdown) con su cola en `QueueSupervisor`, config en `Config`, settings en UI, pero NINGÚN caller desde LiveViews/agents/controllers. The correct pattern: keep the original migration as-is (history is history), add a NEW migration with `mix ecto.gen.migration remove_<field>_from_<table>` (auto-mints the timestamp) with `change do alter table(:table) do remove :field end end`. Both dev and test DBs need to migrate up to the new version. After applying: re-verify `mix compile --warnings-as-errors` + `mix test` + RESTART `mix phx.server` because the running server holds the OLD Ecto schema compiled in memory. The DB-side verification is `psql -h localhost -U postgres -d <db> -c "\d <table>"` — confirm the column is gone.
- **HEEx comment closing tag strips trailing `--%>` on `patch` — easy way to nuke the parser:** when removing a HEEx block via `patch`, the helper's fuzzy matching can swallow the closing `--%>` of an outer `<%!-- ... --%>` comment. Symptom: `Phoenix.LiveView.TagEngine.Tokenizer.ParseError: unmatched closing tag. Expected </div> for <div> at line X, got: </Layouts.dashboard>` even though your visual diff only shows a comment change. Fix: re-read the file (`read_file` with full offset) and visually check that every `<%!-- ` has a matching `--%>` — not just the ones you edited. The pattern that bit me: replacing `<%!-- X --%>` with `<%!-- X -->` (dropping `--%>`) when deleting a multi-line comment block. The patch tool's fuzzy match was greedy enough to match the inner `--%>` as the closing boundary. Safer edit for dropping a comment + the markup below it: use line range or include MORE context in the `old_string` so the fuzzy match doesn't collapse two markers into one.
- **Preload ordering divergence (UI order != routing order):** when a LiveView's `left_join` + `preload` query only orders the parent schema (`order_by: [asc: ma.name]`) but the children (`aps`) are iterated without a join-side `order_by`, Postgres returns them in heap/insertion order. The router's separate query path (`Providers.list_model_providers_for_member/3`) orders by `priority ASC NULLS LAST`, so the visual table and the routing table diverge. User reports it as "the reorder is reversed" or "drag works but routing ignores the order" — but the actual bug is that the visual never matched the routing in the first place. Fix: add `order_by: [asc: ma.name, asc_nulls_last: aps.priority]` to the preload query (note the join binding `aps`, not the schema `ModelProvider`). Verification: load the UI in a browser, drag-reorder, see the new order persist AND requests go to the top provider. Also check the `def model_providers_for(model_alias)` helper that the template iterates — if it returns `model_alias.model_providers || []` without sorting, the helper itself is the secondary ordering bug.
- **Verify field is actually used by runtime BEFORE removal (the "dead field" multi-grep pattern):** before removing a `field :x` from a schema, run THREE greps in separate commands to find all the call sites: (1) `grep -rn ":x\b\|\.x\b" lib/<app>/proxy/ lib/<app>_web/controllers/ lib/<app>/<context>/` — the runtime hot path. If the field has ZERO hits here, it's dead. (2) `grep -rn "field :x" lib/<app>/<schema>.ex` — schema definition. (3) `grep -rn ":x\b" lib/<app>_web/live/<feature>_live.ex` — UI/form. The dangerous false negative is when (1) returns "(no matches)" but (2) and (3) return hits (schema + form) — the field LOOKS live because it has a form input and a display row, but no proxy/controller/context consumer. Symptoms: the UI saves values that are never read back; the UI shows a value that never changes; server-side queries filter by the field but the filter never matches any rows. Common cause: the field survived a refactor that removed the consumer (e.g. a `track_real_usage` boolean survived removing `billing_type` + `routing_strategy` because the schema was kept intact while the logic was deleted). After confirming (1) is empty, removal is safe: migration `remove :x`, schema `field :x` deletion, changeset `cast` drop, form input drop, display badge/label drop. Verification: `mix ecto.migrate`, restart server (see "Server restart" pitfall), `grep -rn ":x\b" lib/ test/` → 0.
- **Server restart after schema/migration change:** `mix phx.server` running in another terminal holds the OLD Ecto schema compiled in memory. After `mix ecto.migrate` + removing a field from the schema, the running server still has the field in `__schema__(:fields)` and will throw `Postgrex.Error: column "x" does not exist` on the first query. Kill the BEAM (`pkill beam` or `kill <pid>`, check `ps aux | grep beam` before) and re-launch `mix phx.server` in background. Verify with `curl -s -o /dev/null -w "%{http_code}\n" http://localhost:4000/` returning 200/302. Mix auto-reload in `dev` does NOT reload migration changes — it only hot-reloads `.ex`/`.exs` source edits.
- **Removing `billing_type` from Provider (cascade after subscription removal):** when subscriptions are removed, `billing_type` (`pay_per_token` | `subscription`) becomes meaningless. Removing it cascades into: (1) `providers_live.ex` — remove `billing_type` select from form, `billing_type_options/0` helper, badge display that showed subscription/pay-per-token; (2) `aliases_live.ex` — `provider_options/1` no longer appends `(#{p.billing_type})` to the display name; (3) `proxy_controller.ex` — remove `billing_type` variable from `stream_costs/2` and `finalize_success/5`; (4) `cost_calculator.ex` — `breakdown/3` becomes `breakdown/2` (drop billing_type param), `real_provider_cost/2` becomes `real_provider_cost/1` (drop billing_type param), update `@spec` signatures, remove the `"subscription"` clause that returned `Decimal.new(0)`, clean up docstrings that mention subscription/pay-per-token distinction. Watch for `@spec` signatures that still list the old arity — the compiler catches `@spec` for undefined functions.
- **Removing an auto-provisioning side-effect from LiveView mount:** a common pattern in Phoenix apps is to auto-create DB records (team + membership + API key) inside a data-loading function (`load_personal_data/2`) when a user has zero memberships — "bootstrap on first visit." When Álvaro asks to make assignment manual (admin assigns teams, users without teams see an empty state), the removal is simple (delete the `if memberships == []` block) BUT the UI gating has a trap: if you gate dashboard sections behind `@teams != []`, admins with zero memberships lose visibility of the full org-wide dashboard. **Fix:** add a `has_access` assign = `user.global_role == "admin" or teams != []` in the data-loading function. Gate UI sections (period selector, endpoint info, metrics, charts) behind `@has_access`, NOT `@teams != []`. Gate the empty-state message behind `@teams == [] and not @has_access` (so admins with no teams don't see "contact the admin" — they see the normal dashboard). The `else` branch of the teams `if/else` in the template handles both "admin with no teams" (shows empty teams list but full metrics) and "user with teams" (shows team cards + metrics). Test flip: assertions that checked for auto-created artifacts (`assert html =~ "General"`, `assert html =~ "Reemplazar"`) become `refute html =~ "General"` + `assert has_element?(view, "#no-team-state")` + `refute has_element?(view, "#api-usage-info")` + `refute has_element?(view, "#period-selector")`.
- **Restricting regular users to dashboard-only (router + sidebar + rankings):** when the product decision is "regular users only see the dashboard with their own data, no config/stats/teams/logs", three changes are needed beyond the auto-provisioning removal: (1) **Router** — move all non-dashboard routes from `live_session :dashboard` (authenticated) to `live_session :admin` (admin-only `require_admin` on_mount). This includes stats, teams, team_members, logs — everything except `DashboardLive`. Regular users hitting those URLs get redirected to `/dashboard` automatically. (2) **Sidebar** — wrap ALL non-dashboard sidebar links in `<%= if admin?(@current_scope) do %>...<% end %>` in `layouts.ex`. Regular users see only "Dashboard" in the sidebar. (3) **Dashboard template** — hide rankings/tops (`#rankings-grid` with top-teams, top-members, top-models charts) behind `:if={@is_admin}`. Add `assign(:is_admin, user.global_role == "admin")` in mount. Regular users see their own KPI cards + charts but NOT comparative rankings. **Test pattern for redirected routes:** tests that previously did `{:ok, view, _html} = live(conn, ~p"/dashboard/stats")` with a regular user now assert `assert {:error, {:redirect, %{to: "/dashboard"}}} = live(conn, ~p"/dashboard/stats")`. Rename test names from descriptive ("user sees only their own consumption") to behavioral ("regular user is redirected from stats to dashboard").
- **`onclick` clipboard no funciona en non-HTTPS (VPN dev):** `navigator.clipboard.writeText()` requiere secure context (HTTPS o localhost). En VPN de desarrollo sin SSL, el clipboard API falla silenciosamente. Hay dos fixes: (1) **Hook `phx-hook` con fallback legacy** — crear un JS hook que use `navigator.clipboard` si está disponible, si no, usar `document.execCommand('copy')` con un textarea temporal (legacy pero funciona en HTTP). (2) **No usar clipboard del todo** — si el token es one-time, el usuario puede copiarlo manualmente con `select-all` en el `<code>`. Otra opción: usar `window.hermesDesktop.writeClipboard` si estás en el contexto de Hermes desktop. **Problema del botón tapando el token:** un botón absoluto con `pr-12` (3rem) puede no ser suficiente para tokens largos. Usar `pr-24` (6rem) o posicionar el botón fuera del `<code>` con flexbox en vez de absolute positioning.
